# Design

## Context

See `proposal.md` for motivation and scope. The VM Compose currently references local tags for Django, PostgreSQL, Nginx, and Traefik; Redis comes from Docker Hub. `scripts/build-vm-images.sh` builds those tags and can create a local transfer bundle. Portainer deploys `docker-compose.vm.yml`; no workflow currently publishes production images to a registry.

## Goals / Non-Goals

**Goals:**

- Publish the four project-built images to `ghcr.io/ryofac` from GitHub Actions using the repository-scoped `GITHUB_TOKEN`.
- Publish a multi-platform manifest for `linux/amd64` and `linux/arm64`, with immutable commit-SHA tags and a convenient `main` tag.
- Keep packages private, link them to the source repository, and keep registry read credentials out of repository files and workflow secrets.
- Let the VM Compose select one common image tag and let local bundle builds remain usable through image overrides.

**Non-Goals:**

- Publish Redis to GHCR, run remote deployment or migrations, or contact the Oracle VM/Portainer from GitHub Actions.
- Remove the manual local bundle path or change product/runtime behavior.
- Make packages public or store a VM registry credential in GitHub Actions.

## Decisions

### Push images directly with Buildx

The workflow will authenticate to `ghcr.io` with `docker/login-action` and `GITHUB_TOKEN`, granting only `contents: read` and `packages: write`. Buildx will push the Django, PostgreSQL, Nginx, and Traefik Dockerfiles as multi-platform images. Each package receives `org.opencontainers.image.source=https://github.com/ryofac/pixu` so GitHub can associate it with the repository. The existing artifact-upload step is removed from this workflow; the local script remains the offline fallback.

Alternative considered: publish only the compressed `docker save` bundle. That retains a manual transfer/load step and does not let Portainer pull an image update directly.

### Use commit and branch tags

Each successful push to `main` will publish the same multi-platform manifest under `sha-<full commit SHA>` and `main`. `PIXU_IMAGE_TAG` selects the tag in Compose and defaults to `main` for convenience; production operators can pin the exact SHA to make a deployment reproducible. No `latest` tag is needed.

### Keep package access private and credentials separated

The workflow token can publish the packages without a PAT. Newly created GHCR packages default to private; the workflow must not change that visibility. For an existing unlinked package, repository Actions access must be granted before a workflow can update it. The Oracle/Portainer pull credential is a separate GitHub PAT classic with only `read:packages` and package read access. It is configured in Portainer as an authenticated `ghcr.io` custom registry or in the VM Docker credential store, never in `.env.vm` or source control.

### Update Compose while preserving local image overrides

The four Pixu services will use `ghcr.io/ryofac/<image>:${PIXU_IMAGE_TAG:-main}` as their defaults. Existing `PIXU_DJANGO_IMAGE`, `PIXU_POSTGRES_IMAGE`, `PIXU_NGINX_IMAGE`, and `PIXU_TRAEFIK_IMAGE` overrides remain supported for local image tags generated by `scripts/build-vm-images.sh`. Redis remains `redis:7.2`.

## Risks / Trade-offs

- [Private pulls fail if Portainer does not send registry credentials] → Document adding `ghcr.io` with a read-only PAT and selecting that registry for the stack; validate with the supported Portainer path before production rollout.
- [A mutable `main` tag can move between deploys] → Also publish a full-SHA tag and document pinning `PIXU_IMAGE_TAG` to it.
- [A multi-platform build can fail if an upstream base image lacks one target architecture] → Build both architectures in CI and keep the local tar script available as an operational fallback.
- [Source image metadata or package settings can accidentally expose images] → Keep packages private, use only workflow-scoped write permission, do not call a visibility-changing API, and verify package visibility after first publication.
- [Existing Portainer stack still points at local image tags] → Update stack images and configure private registry access before redeploying; keep the previous SHA or local bundle for rollback.

## Migration Plan

1. Add source labels and the GHCR publish workflow; run the multi-platform build and verify four private packages and both tags.
2. Configure Portainer/VM registry read access without placing the PAT in `.env.vm`.
3. Update the stack to use `PIXU_IMAGE_TAG=sha-<commit>` and the GHCR images, then pull and deploy manually in Portainer.
4. Roll back by pinning a prior SHA or by setting the existing per-image overrides to the local tags loaded from a bundle. The local build-and-bundle script remains available throughout.
